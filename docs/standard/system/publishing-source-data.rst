Publishing source data alongside BODS
=====================================

.. note::

   This page is guidance. It does not add requirements to the standard.

Most publishers of BODS data hold beneficial ownership information in a system of their own: a register's relational database, a document store, or the forms that declarants file. BODS data is generated by mapping that information into the BODS data model.

Any mapping loses some detail. A register's own terms, such as the difference between a founder and an owner, or a category of control set out in national law, may have no exact equivalent in BODS. A value may be split, merged, normalised or translated on its way into a Statement. Users who map BODS data into another schema of their own then make a second mapping, and the losses add up.

Publishers are therefore encouraged to publish their in-house format alongside BODS data, rather than replacing it with BODS. Doing so lets users:

* check how the publisher mapped its data into BODS, and report errors in the mapping
* fall back to the source where BODS cannot hold a detail they need
* map directly from the source into their own schema where that suits their use better

The in-house format does not need to be elaborate. A regular export from the system that holds the data, such as CSV files from a database or JSON documents from a document store, is enough, provided it is documented.

What to publish
---------------

Where possible, publish:

* **the in-house data**, in the format the publisher's system produces, on the same schedule as the BODS data so that the two describe the same state of the register
* **documentation of the in-house format**, explaining each field and code in the publisher's own terms, with reference to the law or form that defines it
* **the mapping**, a description of how each in-house field and code is represented in BODS, including fields that are not mapped and values that are transformed

The in-house data should be subject to the same checks on personal data as the BODS data. Publishing a source export does not change what may lawfully be made public. Fields withheld from the BODS data for privacy or security reasons should also be withheld from the in-house export. See :ref:`guidance-identifiers` for related guidance on person identifiers.

Linking BODS data to the source
-------------------------------

BODS data and in-house data are most useful when a user can move from one to the other. The schema provides for links at three levels.

**Dataset.** ``publicationDetails.publisher.url`` is the URL where details of the full dataset, or of the publisher, can be found. The page at this URL can list both the BODS data and the in-house data, with their documentation and the mapping. See :ref:`schema-publicationdetails`.

**Record.** ``source.url`` is the URL from which the information in a Statement was fetched, or which gives more detail on how it was sourced. Where the publisher's system has a page or API endpoint for each record, use that URL, so that each Statement points at the record it was generated from. See :ref:`schema-source`.

**Field.** An :ref:`Annotation <schema-annotation>` can explain how a particular field relates to the source. Use the motivation 'transformation' where a value was changed on its way into BODS, with the method in ``description`` and, where useful, the result in ``transformedContent``. Use the motivation 'linking', with a ``url``, to point at the source record or at the documentation of a source field or code.

For example, a register that publishes the following Statement alongside its in-house export lets a user find the source record, the dataset page and the meaning of the register's own category of interest:

Keeping the in-house data and BODS data in step
-----------------------------------------------

Users will compare the two, so they should agree. Publishers are encouraged to:

* generate both from the same extract of their system, and say when that extract was taken
* use the same identifiers for companies and people in both, or publish a table that links them. Statement and record identifiers can be based on internal identifiers, as described in :ref:`generating-statements`.
* publish a new version of the mapping whenever it changes, so that users can tell which mapping produced which BODS data

Republishers
------------

Organisations that republish BODS data generated by others, or that map another publisher's data into BODS, are encouraged to keep the original reachable in the same way: set ``source.url`` to the record they read, use ``source.retrievedAt`` to say when they read it, and record their own changes to values with Annotations.
